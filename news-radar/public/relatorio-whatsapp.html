O QUE FOI CONSTRUÍDO

PARTE A — Filtro de privacidade (opção B)

Regra única em app/Services/Jr/CapturaFiltro::aceita(), aplicada em dois pontos (defesa em profundidade):

1. Na rota /api/jr-pauta-capture — mensagem que não passa o filtro nem vira arquivo no disco (privacidade na origem; responde 200 igual pro Z-API não reenfileirar).

2. No jrpauta:ingest — mesmo que algum arquivo individual já tenha escapado pro disco no backlog antigo, não vira linha no banco.

A regra:

  • ✅ Só grupo (is_group=1). Conversa individual nunca é gravada.
  • ❌ Denylist nominal (config jrlink.captura.ignorar_chats): Raspador (anti-loop), Família Buscapé 🤪, Serviços Executados, Lesadas pela JANNA/ VIRTUOSA oficial, Ideias Mkt Alex.
  • ❌ Denylist por regex (jrlink.captura.denylist_regex): /Jornal Raz[aã]o\s*#JR\d+/iu — os 56 grupos de distribuição.

Anti-loop preservado e reforçado: o corte do Raspador é pelo NOME do chat, não pelo from_me — porque o Z-API entrega a mensagem da própria instância com from_me=0 (o flag não é confiável). A contraprova testou exatamente esse caso.

PARTE B — Religar a captura

  • jrpauta:ingest ganhou --incremental: processa só os arquivos novos desde um cursor (gravado em storage/app/jr-pauta-capture/.ingest-cursor), em vez de reler os 56k do backlog a cada ciclo.
  • Entrou no scheduler (routes/console.php): jrpauta:ingest --incremental a cada 5 min.
  • O webhook não precisou de nada — já estava vivo. (Se um dia a instância cair, aí sim você reconecta o WhatsApp no painel Z-API; hoje não é o caso.)

PARTE C — Ponte captura → Radar

Novo comando jrpauta:bridge-radar (agendado :02,:32, logo antes do juiz :05,:35):

  • Pega release de TEXTO de grupo permitido em jr_pauta_capturas e promove pra jr_link_extracao com origem=whatsapp.
  • Usa o mesmo molde do canal Instagram: categoria=concorrente, gate de corpo + régua concorrente_feed, dedup permanente por url_hash (url canônica sintética wa://capture/<hash> — nunca colide com o caminho de links do jrlink:extract).
  • Janela pela HORA DA CAPTURA (momment), não pelo created_at, pra o backlog de 13 dias não entrar todo de uma vez e estourar o juiz. Cap por run (200) + janela 72h (configuráveis por env).
  • Pega só release sem link http (link já é tratado pelo jrlink:extract, que também grava origem=whatsapp) — os dois caminhos são complementares.

Roteamento no juiz (igual ao IG, commit 988bf83): em jrlink:juiz, todo item origem=whatsapp não-julgado entra DIRETO no juiz, pulando o gate coarse (que foi calibrado pra manchete de portal e mataria o release antes de avaliar). Um aviso curto no INPUT do item diz que é mensagem de grupo/release, avaliar o assunto e não o formato.

> Prompt BASE do juiz intocado. app/Services/Jr/JuizLlm.php ficou byte-a-byte idêntico (md5 51a09ef0… antes e depois; heredoc do prompt bc67d5d6… idêntico). prompt_versao segue v3 — não foi bumpado. Só mexi em roteamento + aviso no input (a mesma estratégia já validada no canal Instagram). Feed/portais inalterados.
